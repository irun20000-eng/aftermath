# 학습지 제작 파이프라인

`.claude/playbook/` 을 실행 가능한 절차로 만든 오케스트레이션 스킬.

## 먼저 읽는다

```
.claude/playbook/lessons/PITFALLS.md        기술 함정
.claude/playbook/lessons/DECISIONS.md       제품 결정 선례
.claude/playbook/lessons/COMMUNICATION.md   보고·질문 방식
.claude/playbook/profiles/_generic.md       공통 규칙
.claude/playbook/profiles/<과목>.md          과목 규칙
```

이 다섯을 읽지 않고 시작하지 않는다. 여기 있는 내용을 다시 발견하느라 지난 사이클에서
**커밋 87건 중 32건(37%)** 이 수정 커밋이었다.

---

## 파이프라인

```
Phase 0  스코핑        ◀ 선생님 개입 ①
Phase 1  추출     ─┐
Phase 2  제작     ─┼─ 단원별 독립 진행 (장벽 없음)
Phase 3  검증     ─┘
Phase 4  통합
Phase 5  감사
Phase 6  납품        ◀ 선생님 개입 ②
Phase 7  회고
```

### Phase 0 · 스코핑 — 인터뷰 1회

`playbook/10_PLAN.md` 의 8문항을 **한 번에** 묻는다. 한 문항씩 물으면 왕복이 그만큼 늘어난다.
4·5·7번(배치 / 독립 차시 여부 / 인쇄 용도+기기)은 되돌리기 비싸므로 반드시 명시적 답을 받는다.

`templates/기획안.md` 를 채워 제시하고 착수 승인을 받는다.
**여기서부터 Phase 6까지는 묻지 않는다.**

### Phase 1~3 · 단원별 파이프라인

**단원이 병렬 단위다.** 단원끼리 의존이 없으므로 장벽(barrier)을 두지 않는다.
Ⅰ-1이 검증 중일 때 Ⅱ-1은 이미 제작에 들어간다.

| Phase | 역할 | 산출 |
|---|---|---|
| 1 추출 | 원자료 → 문항·정답·난이도·그림 | 구조화 데이터 |
| 2 제작 | 데이터 → 산출물 HTML | 빌드 스크립트 + 결과물 |
| 3 검증 | A정적 → B렌더 → C수학 → D범위 | 통과/실패 + 수정 |

**검증 실패 시 스스로 고치고 재검증한다.** 선생님께 보고만 하고 멈추지 않는다.

**단원이 3개 이하면 파이프라인을 만들지 말고 순차로 한다.** 오버헤드가 더 크다.

### Phase 4 · 통합

모든 단원이 끝나야 하는 유일한 단계.

- 단원 간 이전/다음 링크
- 모음 페이지 활성화
- 메인 인덱스 / 교사용 인덱스 / 교사용 Nav 인덱스 / 묶음 PDF
- **네 곳의 배치 순서를 일치시킨다**

문서 합성이 포함되면 `PITFALLS E`(전역·id·fixed 3종 충돌)를 반드시 확인한다.
통합본의 카드 폭이 개별 파일과 다르면 개별에서 통과한 검증이 무효가 된다 (E-5).

### Phase 5 · 감사

"무엇이 빠졌는가"만 보는 단계. 만든 사람의 눈으로는 안 보인다.

- 기획안 대비 누락된 산출물
- 검증하지 않은 파일
- 갱신했어야 하는데 안 한 연동 대상
- 이번 변경과 무관하게 발견된 기존 결함

### Phase 6 · 납품

`templates/검수보고서.md` 를 **숫자로 채워** 제시 → 승인 → PR → squash 머지 → 드라이브 반영.
드라이브는 **새 폴더에만** 업로드한다 (`playbook/50_DELIVER.md`).

### Phase 7 · 회고

`templates/회고.md` 를 채우고 **플레이북을 갱신한다.** 이 단계를 빼면 다음에 같은 함정을 밟는다.

## 에이전트 배치

`Agent` 도구로 호출한다. 각 에이전트는 자기 컨텍스트만 갖는 대신 깊이 있게 본다.

| Phase | 에이전트 | 개수 |
|---|---|---|
| 1 추출 | 범용 (extractor 프롬프트) | 단원당 1 |
| 2 제작 | 범용 (author 프롬프트) | 단원당 1 |
| 3 검증 C | `problem-evaluator` | 재계산 대상 문항당 1 |
| 3 검증 D | 범용 (교육과정 대조) | 단원당 1 |
| 5 감사 | `worksheet-auditor` | 1 |

### 정답 검증을 강하게 할 때

서로 다른 관점의 검증자에게 **"이 정답을 반박해 보라"**고 시키고, 과반이 반박하면 재계산한다.
같은 프롬프트 3개보다 **관점이 다른 3개**(계산 / 조건 해석 / 단위·부호)가 훨씬 잘 잡는다.

---

## 대규모 병렬이 필요할 때

단원이 8개 이상이거나 문항이 100개를 넘으면 `Workflow` 도구로 그래프를 짤 수 있다.

**단, `Workflow` 는 선생님의 명시적 동의가 있을 때만 호출한다.** 에이전트를 수십 개 띄운다.
동의 없이는 `Agent` 를 순차·소규모 병렬로 쓴다.

동의를 받았다면 파이프라인 형태로 짠다 (장벽 없이):

```
pipeline(단원목록,
  단원 => agent(추출 프롬프트, {phase:'추출', schema:...}),
  data => agent(제작 프롬프트, {phase:'제작'}),
  built => agent(검증 프롬프트, {phase:'검증', schema:...})
)
```

`parallel`(장벽)은 **모든 단원 결과가 한꺼번에 필요할 때만** 쓴다 — 즉 Phase 4 통합 직전.

---

## 하지 않을 것

- 검증(Phase 3) 없이 완료 보고
- 한 파일만 고치고 끝내기 — 같은 성격의 파일이 몇 개인지 **먼저 센다**
- 일괄 작업 후 표본 검사 — **전 파일 검증**
- 범위 밖 결함을 임의로 수정 — 보고하고 지시를 받는다
- 큰 HTML을 `Read` 로 통째 열기 — `grep` + 슬라이스
- 스코핑과 최종 승인 사이에 질문하기
